# Bark 0.8.0, Lightning send options and payment requests: v0.6.0

Engineering plan and upstream delta: [Bark 0.8.0 plan](../plans/24-bark-0.8.0-payments.md).

Implemented: Bark pinned at lib-0.8.0 (`959a489f`). Movement ids from
`sendArkoorPayment`, `sendOnchain` and offboards. `LightningSendOptions` (`wait`,
`retryForSecs`) on every Lightning pay method. `parsePaymentRequest` with typed
per-option errors and `invalidPaymentRequest`, `estimatePaymentFee(s)`,
`sendPayment`, `bip321Uri` and `debugInfo`. Every call goes to the upstream
method; the only wrapper dispatch is onchain `sendPayment`, which keeps the
movement id upstream's dispatcher drops. RegTest images: captaind and Bark CLI
`nightly-2026-10-22`. The captaind image reports `0.7.1-dev+5d9c4eda`, which
differs from the 0.8.0 server only in a telemetry allow-list and a webpki-roots
bump. The CLI image reports `0.7.1-dev (38aecc89)`.

Environment: live checks used a task-owned Compose project
`bark-bolt-ffi-v060` (Ark 127.0.0.1:3735, Bitcoin 127.0.0.1:19543). Other
agents' `noah-bark08-*` and `scripts-*` stacks, the repository's existing
`bark-bolt-ffi` stack, the shared booted iPhone simulator and its runner, the
`noah-sr-*` AVDs and another agent's `emulator-5592` were not touched. The apps
ran on a task-created simulator (`Bark v060 iPhone`, iOS 27.0) and AVD

## Findings during validation

- The first full Rust run against the isolated stack failed three library
  live tests. They hard-coded ports 3635/19443 while their funding helper
  followed `COMPOSE_PROJECT_NAME`. Every live test now reads `ARK_PORT` /
  `BITCOIN_PORT`, as the Swift/Kotlin contracts already did.
- A Lightning payment sent right after a live test mined about 226 blocks
  force-closed the LND–CLN channel. CLN, still at height 243, offered an HTLC
  with expiry 324; on reaching height 469 it hit the deadline. CI runs the
  same order. `scripts/ark-dev.sh wait-lightning-sync` waits until LND and CLN
  reach the Bitcoin tip; the new Rust/Swift/Kotlin tests call it before paying.
- Independent source review (Claude subagent, read-only) found, and this change
  fixes:
  - Upstream `parse_payment_request` unwraps BOLT12 offer amounts. A
    USD-priced offer panicked across the FFI, because `run_async` re-raises
    task panics. The wrapper catches that panic.
  - Upstream debug-asserts a non-empty option list. The wrapper rejects
    requests without options. Both cases return `invalidPaymentRequest`.
  - `bip321Uri` held the onchain write lock through the invoice's server
    call. The onchain address is now derived first when an Ark address or
    invoice is requested.
  - Options that leave no destination are rejected.
  - Bark accepts up to twice an invoice's amount when an amount is passed.
    The docs and examples now pass the request's amount, and only when
    `requiresAmount` is set.
  - The Kotlin test timeout was raised to 300s.
  - The reviewer confirmed deterministic option order, sat/msat handling, the
    onchain network check, error-code ordinal stability and the absence of a
    deadlock.
