# Swift/Kotlin-only BoltFFI migration assessment

Investigated 2026-10-18 for the proposed Swift/Kotlin-only Bark bindings migration. The initial inspection used source research and isolated Rust macro compile probes. A follow-up native proof now generates and executes Swift/Kotlin consumers; the production Bark bindings have not been migrated.

**Recommendation:** proceed with a small native consumer proof before committing to the full switch. Removing the other consumer languages is straightforward; replacing UniFFI requires changes to object ownership, options, errors, and native packaging. The existing Rust wallet core can largely stay in place. This is a coordinated migration across two repositories, not just a dependency change in this one.

**Follow-up result:** the [native proof](../experiments/boltffi/README.md) passed with BoltFFI 0.31.1, Rust 1.90.0, Swift 6.4 and Kotlin 1.9.24/JDK 17. Swift executed through generated SwiftPM/XCFramework output, and Kotlin through the packaged desktop JNI library. Both exercised concrete async factories, a Tokio timer, record defaults, full-range u64 values, retained callbacks, typed/unexpected callback errors, nested notification payloads, explicit and foreign cancellation, reuse and object release. Android arm64 JNI packaging and iOS device/simulator Rust slices also built; generated Swift compiled for an iOS 14 simulator target using SwiftPM's native build engine. Generated bindings were not patched. This clears the representative native-boundary proof step; a real Bark adapter port and mobile runtime validation remain.

Two implementation details are now explicit: the proof moves notification cancel-slot cleanup into its Drop guard so foreign cancellation cannot skip it; the current production holder still needs that adaptation. BoltFFI also hardcodes macOS 13 in its generated Swift package, while the existing SDK declares macOS 12. Its release package handling must preserve or intentionally change that platform contract. The installed Swift 6.4 default build engine rejected iOS 14, but the native engine compiled it; release-toolchain support still needs verification.

## What to remove and what to retain

In **this repository**:

- Delete `src/wasm/`: 7 files and **1,592 of 8,846 Rust source lines** at the inspected commit. This removes the browser wallet, IndexedDB adapter, JS notifications/functions, and browser logger.
- Remove `wasm-web`, its direct optional dependencies (`wasm-bindgen`, `wasm-bindgen-futures`, `serde-wasm-bindgen`, `tsify`), WASM upstream feature wiring, browser-specific conditional code, and the WASM CI job. Transitive dependencies may still legitimately retain similarly named crates in Cargo.lock; acceptance should concern active dependencies/features, not a text search for every name.
- Replace the UniFFI dependency, scaffolding, attributes, defaults, error representation, and `muniffi` module naming. With one binding layer, the mutually exclusive feature architecture can be simplified to a normal native configuration; optional language features are unnecessary unless another actual consumer requires them.
- Keep native SQLite, TLS, BDK, callback transaction validation, the Tokio runtime, the core wallet/onchain logic, and its upstream Bark revision. Keep Serde/serde_json where used for metadata, destinations and existing serialization tests; these are not exclusively browser dependencies.
- Fix `core::wallet::OpenArgs` and `into_bark`: `datadir` is currently gated on `uniffi`. Simply removing that feature could lose the native datadir/locking setup. Retain native lock-manager paths when deleting browser branches.
- Refresh package description/version metadata, the UniFFI-version tag convention, README, lockfile, CI and toolchain target list. The current toolchain comment explicitly describes Dart's Native Assets workflow.

In **the companion repository**:

- Remove `dart/`, `golang/`, `react-native/`, and `wasm/`, plus their examples, generation targets, release/publish jobs and Nix profiles. Inspect shared release scripts and build images before pruning dependencies.
- Update both Swift/Kotlin Rust wrapper crates, generated sources, binding configurations, package metadata and release artifacts. Both wrappers currently pin this crate and UniFFI 0.31.1; leaving them unchanged would retain the previous generator. [Swift wrapper](https://gitlab.com/ark-bitcoin/bark-ffi-bindings/-/blob/157b0fcda0a0a5782ad2904ed3002a7080293047/swift/rust/Cargo.toml), [Kotlin wrapper](https://gitlab.com/ark-bitcoin/bark-ffi-bindings/-/blob/157b0fcda0a0a5782ad2904ed3002a7080293047/kotlin/rust/Cargo.toml).
- Repair the CI dependency graph: **both Swift and Kotlin builds currently have `needs: build-golang`**. The shared release job also requires all removed language builds. Deleting Go or its job alone would break the remaining pipeline. [Release pipeline](https://gitlab.com/ark-bitcoin/bark-ffi-bindings/-/blob/157b0fcda0a0a5782ad2904ed3002a7080293047/.gitlab/release.yml).

Avoid merging or flattening the core/native modules as part of the generator switch. The existing separation provides a useful place to adapt BoltFFI without rewriting wallet behavior.

## Current API incompatibilities verified in source

1. **Exported `Arc<T>` class signatures need redesign.** Bark returns `Result<Arc<Self>, Error>` from `Wallet::open`, `OnchainWallet::default`, and `OnchainWallet::custom`; it returns `Arc<NotificationHolder>` from `Wallet::notifications`. BoltFFI scans `Arc<T>` as an explicit Arc type, and its binding lowering rejects `Arc<T>`/`Box<T>` value types unless they contain a callback `dyn Trait`. This differs from internal shared ownership: BoltFFI itself retains exported class handles, and application structs can still contain Arcs. Likely adaptation: return concrete exported objects (`Self`, `NotificationHolder`) while retaining shared state internally. [Scanner `type_expr.rs`](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_scan/src/type_expr.rs#L145), [binding `lower/types.rs`](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_binding/src/lower/types.rs#L36), [generated class handle implementation](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_macros/src/expansion/wrapper/class.rs#L178). Local surfaces: `src/muniffi/wallet.rs`, `src/muniffi/onchain.rs`.

2. **`WalletOpenArgs.onchain: Option<Arc<OnchainWallet>>` cannot remain an ordinary record field.** The Arc already hits the rule above. Even replacing it with a bare class inside a wire-encoded record reaches unsupported class-handle codecs. Keep the value fields in `WalletOpenArgs`, and move the wallet to a direct object parameter. A scratch async factory with a required `&Onchain` argument compiles; an `Option<Onchain>` parameter also compiles, but its ownership semantics need consumer verification. **`Option<&Onchain>` fails scanning**, so it is not a verified replacement for the current optional shared handle. A factory without an onchain argument plus a factory borrowing an onchain object is a candidate that preserves sharing without introducing an options-builder class. [Swift read](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_backend/src/target/swift/codec/read.rs#L162), [Swift write](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_backend/src/target/swift/codec/write.rs#L159), [Kotlin read](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_backend/src/target/kotlin/codec/read.rs#L164), [Kotlin write](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_backend/src/target/kotlin/codec/write.rs#L337).

3. **`NotificationHolder::next_notification(self: Arc<Self>)` needs a supported receiver.** The scanner classifies a receiver without `&` as owned, including typed `self: Arc<Self>`. Lowering then rejects owned class receivers. An async `&self` method compiles in the scratch probe; verify its retained lifetime while awaiting and after foreign references are released. [Receiver scan](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_scan/src/items/signature.rs#L83), [owned receiver rejection](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_binding/src/lower/methods.rs#L364). Local surface: `src/core/notification.rs:73`.

4. **The current flattened error is not a matching error representation.** Bark deliberately exports only the formatted cause chain from `Error::Inner(anyhow::Error)` through UniFFI `flat_error`. BoltFFI documents strings and `#[error]` records/enums whose fields cross the binding boundary; the current anyhow payload is not such a wire field. Introduce an FFI error carrying `message: String`, or return string errors at the boundary. Preserve the `{:#}` cause-chain formatting. Typed callback errors additionally need conversion from `boltffi::UnexpectedFfiCallbackError`; upstream demonstrates this explicitly. [Error representations](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/errors.mdx#L17), [callback error example](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/examples/demo/src/results/error_enums.rs#L87). Local surface: `src/error.rs`.

These source-established incompatibilities were corroborated with isolated `cargo check` probes using BoltFFI 0.31.1 and Rust 1.90.0: Arc factory and Arc record field report `opaque Rust pointer container`; bare class in record reports `unsupported expansion: codec node`; typed Arc receiver reports `owned class receiver`; anyhow error payload reports `unsupported source type anyhow::Error`. A concrete-Self async factory passes. These are Rust macro checks only, not host code generation or runtime tests. Scratch evidence: `/tmp/bark-boltffi-probe.qsCoUP/results.json` and its corresponding `.txt`/`.log` files.

An additional probe extracted all **53 ordinary data declarations** from `types.rs` and `config.rs`, removed binding/serialization attributes and conversion implementations, added BoltFFI `#[data]`, and exported an echo function for each type. The first compile required `Copy` on five scalar records: **`Balance`, `OnchainBalance`, `FeeRates`, `BoardFees`, and `LightningReceiveFees`**. Adding `Copy` to those five made all 53 compile. This establishes a practical mechanical path for those data shapes; it does not verify their generated Swift/Kotlin layout, Serde behavior or defaults. A combined adapted-signature probe also compiled concrete async factories, a message-bearing error, both kinds of synchronous callback and a borrowed async receiver. Callback retention/execution was not tested.

## Capabilities that match this repository

**Records, optional values, vectors, scalar values and data enums:** BoltFFI uses `#[data]` for copied structs/enums and `#[export]` for functions and class impls. Data enums with payloads and nesting are documented and have native consumer examples. This fits Bark's many value records and enums, including nested notification and VTXO state payloads. Defaults use `#[boltffi::default(...)]`; optional record fields default to nil/null. Translate each explicit UniFFI default. Release 0.31.1 adds Swift/Kotlin parameter defaults and fixes Kotlin constructor generation, directly relevant to this API. Inspect generated call syntax instead of assuming source compatibility. [Records, enum and defaults documentation](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/records.mdx), [Swift enum tests](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/examples/platforms/apple/Tests/DemoConsumerTests/enums/DataEnumTests.swift), [Kotlin value tests](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/examples/platforms/kotlin/src/test/kotlin/com/boltffi/demo/DemoValueTypesTest.kt).

**Async functions and methods:** generated Swift uses async/await, Kotlin uses suspend functions. Async factories exist in upstream's demo as functions returning concrete `Self`; the demo explicitly lists missing Swift and Kotlin consumer coverage for that async initializer case. Treat async wallet opening as a required spike, not a proven drop-in API. Swift/Kotlin creation syntax may change. [Async documentation](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/async.mdx), [async factory and coverage gaps](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/examples/demo/src/classes/async_factory.rs).

**Foreign callback traits:** `#[export]` traits can be held as `Arc<dyn Trait>` or `Box<dyn Trait>`. Retention for stored traits is documented. Sync callbacks with `Result<(), E>`, `Result<T, E>`, string and record arguments have examples and Swift/Kotlin tests. This matches Bark's synchronous 10-method custom-onchain-wallet callback and synchronous logging callback. Async callback traits and fallible async callbacks also exist upstream, but Bark does not currently require them; changing callback sync/async behavior would be a separate API change. [Callback ownership and async traits](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/callbacks.mdx#L351), [fallible callback declarations](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/examples/demo/src/callbacks/errors.rs), [Swift callback error tests](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/examples/platforms/apple/Tests/DemoConsumerTests/callbacks/CallbackErrorTests.swift), [Kotlin callback error tests](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/examples/platforms/kotlin/src/test/kotlin/com/boltffi/demo/CallbackErrorsTest.kt).

The exported API already uses strings for Bitcoin addresses, transaction IDs, PSBTs and other external types, and has no exported maps. No new custom-type or map adapter is needed for this migration. Retain the existing parsing and transaction validation.

## Tokio, cancellation and lifetime risks

BoltFFI supplies a foreign-driven future polling mechanism, **not a Tokio runtime**. Tokio-dependent code still needs a running runtime/reactor. Keep `src/muniffi/runtime.rs`'s runtime/offload behavior through the migration; dropping `async_runtime = "tokio"` attributes without reviewing every async entry point is insufficient. [Runtime documentation](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/async.mdx#L359).

Swift task and Kotlin coroutine cancellation reach BoltFFI's wrapper future. That does not prove cancellation stops Bark operations: local `run_async` spawns a Tokio task then awaits its JoinHandle; dropping a Tokio JoinHandle detaches the task, which keeps running. Preserve or explicitly define those semantics before adding abort-on-drop behavior to wallet operations. NotificationHolder uses a separate oneshot cancel operation and must remain reusable after cancel; test its RAII guard and cancel slot after foreign task cancellation. [BoltFFI cancellation](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/async.mdx#L291), [Tokio JoinHandle behavior](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html#cancel-safety).

Logger callbacks may arrive on Rust worker threads. Verify threading expectations and log-level mapping. The current `replace_sink` deliberately calls `mem::forget(previous)` to survive React Native reloads: replaced or cleared callbacks are never released. Once React Native is removed, revisit that workaround with Swift/Kotlin ownership tests instead of preserving the intentional leak by default. Keep the existing rule that locks are released before invoking callbacks. Verify wallet destruction still stops its daemon and callback wallets remain alive for their Rust-held lifetime. Local evidence: [logger](../src/muniffi/logger.rs#L71) and [wallet Drop](../src/muniffi/wallet.rs#L1094).

## Packaging consequences

**Apple:** `boltffi pack apple --release` builds static XCFramework slices and SwiftPM output. iOS device/simulator and optional macOS slices are configurable; SwiftPM supports self-contained, bundled-wrapper, split-binary and remote binary layouts. This can replace the hand-built Apple package pipeline after preserving package/module names, deployment versions and public wrapper behavior. [Pinned packaging docs](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/packaging.mdx#L203).

**Android:** `boltffi pack android --release` builds Kotlin sources, generated JNI glue and linked `jniLibs/<abi>/*.so`. Kotlin's native access therefore changes from this repo's UniFFI/JNA approach to JNI. The packager compiles/links the JNI glue; it is not enough to rename the previous Rust .so. The inspected output is sources plus native assets, not a published AAR: retain or implement the Gradle AAR/Maven publication layer. Set the Android minimum SDK explicitly to preserve existing support; upstream's default is 24. [Configuration](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/configuration.mdx#L310), [Android native linker](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_cli/src/pack/android/link.rs#L78).

**Kotlin desktop/JVM:** do not remove Linux targets just because other consumer languages are removed. Standalone Kotlin's config has `desktop_loader = "bundled"` by default, plus opt-in `[targets.android.kotlin.desktop_pack] enabled = true`. `pack android` then writes `desktopJniLibs` using the shared `[targets.java.jvm].host_targets` configuration; this does not require shipping a Java consumer API. `desktop_pack` defaults false. Preserve the current Kotlin script's **Linux x86_64 and macOS host builds**, and package JNI resources in its JVM artifact. The root Rust toolchain also lists Windows targets, but the current Kotlin script explicitly skips Windows: those entries do not establish a current Kotlin Windows product. If adding or retaining Windows support is desired, validate it separately; BoltFFI's desktop host list includes Windows x86_64 but not Windows ARM64. [Current Kotlin build script](https://gitlab.com/ark-bitcoin/bark-ffi-bindings/-/blob/157b0fcda0a0a5782ad2904ed3002a7080293047/kotlin/generate-bindings.sh#L80), [Kotlin config](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_cli/src/config/targets/kotlin.rs#L10), [desktop pack flow](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_cli/src/pack/android/mod.rs#L156), [shared host packaging](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi_cli/src/pack/java/plan.rs#L470).

Preserve the actual companion package contracts: its root Package.swift declares **Swift tools 5.9, iOS 14 and macOS 12**, while Kotlin's Gradle modules set **Android minSdk 24 and JVM 17** and depend on JNA 5.15.0. Some README examples still describe older sync constructors and older error variants; use current Rust signatures and build manifests as the migration baseline. Keep the `Bark` Swift product/module and existing Maven coordinates unless a deliberate breaking rename is wanted. [Package.swift](https://gitlab.com/ark-bitcoin/bark-ffi-bindings/-/blob/157b0fcda0a0a5782ad2904ed3002a7080293047/Package.swift), [Android Gradle](https://gitlab.com/ark-bitcoin/bark-ffi-bindings/-/blob/157b0fcda0a0a5782ad2904ed3002a7080293047/kotlin/bark-android/build.gradle.kts), [JVM Gradle](https://gitlab.com/ark-bitcoin/bark-ffi-bindings/-/blob/157b0fcda0a0a5782ad2904ed3002a7080293047/kotlin/bark-jvm/build.gradle.kts).

Avoid the experimental Kotlin Multiplatform path for this migration: its documented admitted surface is much smaller than the async/object/callback wallet API. Plain Kotlin bindings with JNI can serve Android/JVM without introducing KMP. [KMP limitations](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/docs/src/content/docs/experimental.mdx).

## Toolchain, maturity and acceptance criteria

BoltFFI 0.31.1 uses edition 2024 and pins its development/CI toolchain to **Rust 1.97.1**; Bark currently pins **1.90.0**. No explicit `rust-version`/documented MSRV was found in the inspected manifests. The pin is evidence of upstream's tested development toolchain, not proof of minimum compatibility. The isolated async factory and other macro probes succeeded on 1.90.0, so no mandatory Rust upgrade has been established. CLI compilation and the complete Bark/native matrix remain untested. Pin CLI and crate to the same release and retain Cargo.lock. An exact facade dependency alone does not lock internal BoltFFI crates: the initial `=0.31.0` facade probe resolved semver-compatible internals to 0.31.1; use the lockfile to make the selected graph reproducible. [Workspace manifest](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/Cargo.toml), [toolchain](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/rust-toolchain.toml), [runtime manifest](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/boltffi/Cargo.toml).

The project is MIT licensed, has Rust CI, native consumer tests and a demo coverage ledger, but remains pre-1.0 and 0.31.0 fixed class ownership and callback exceptions while 0.31.1 fixes Kotlin constructors, native loading and Apple module-map collisions. The concrete coverage gaps above justify validating this wallet's actual shapes before committing to a wholesale switch. This is an adoption-risk inference from source/release evidence, not a claim that the project is unusable. [License](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/LICENSE), [CI](https://github.com/boltffi/boltffi/blob/dda08e1bdf93e3c04d576c072d17e09161fae5df/.github/workflows/ci.yml), [release fixes](https://github.com/boltffi/boltffi/releases/tag/v0.31.1).

Before deleting UniFFI, require both Swift and Kotlin consumer evidence for:

- An async, fallible object factory; ordinary methods; all record/enum payload variants; u64 values and optional/default fields.
- Custom onchain callbacks: record/vector arguments, returned value, `Result<(), E>`, typed error and unexpected foreign exception; callbacks invoked from Rust worker threads.
- Notification receive, explicit cancel, coroutine/task cancel, subsequent receive, concurrent-receive rejection and wallet shutdown.
- Object/callback destruction and daemon stop, including releasing foreign references during an in-flight async call.
- iOS device/simulator plus macOS package import, Android ABI loading from an AAR, and desktop JVM resource extraction/loading on every retained host.

No Bark performance measurement was performed. Upstream microbenchmark speedups are not evidence of an end-to-end improvement for network/storage-bound wallet operations and should not be used to estimate this migration's benefit.

## Suggested migration order

1. **Prove the difficult native boundary in isolation.** Pin BoltFFI crate and CLI 0.31.1; generate, compile and run a tiny Swift and Kotlin consumer with the adapted factories, error, callback and notification shapes. Include an actual Tokio timer/network operation so success is not limited to immediately-ready futures. Resolve async factory syntax, class ownership and platform minimums here.
2. **Port this crate's native layer.** Keep Bark 0.7.1 and the core logic stable. Adapt the identified signatures and scalar records, translate every explicit default, preserve the callback PSBT/output/signature checks and SQLite filename compatibility, and retain shutdown/cancellation controls. Keep the native adapter seam; do not combine this with a wallet-core refactor.
3. **Move the Swift/Kotlin products to BoltFFI.** Replace generation scripts/configuration and Rust wrappers as appropriate, package SwiftPM/XCFramework and Android AAR/JVM JAR, remove JNA, update example apps and consumer tests, and validate artifact loading on the retained platforms. Configure only the requested targets rather than using `pack all`.
4. **Remove the unwanted consumers and old infrastructure.** Delete WASM/browser code and other language packages, remove UniFFI and its version-specific release wiring, repair CI `needs`/release jobs, and prune toolchain/Nix/build-image inputs against the retained Swift/Kotlin platform matrix. Ship this as a breaking SDK release unless consumer compatibility is explicitly demonstrated.

This order is a validation sequence, not a recommendation to maintain two binding generators permanently. No project schedule estimate is justified until the native consumer proof establishes whether upstream changes are needed.

## Initial inspection verification (before the native proof)

- Read all source/configuration paths relevant to exports, runtime, callbacks, persistence, features and CI, and inspected the pinned companion package/build/release manifests read-only.
- `RUSTUP_TOOLCHAIN=1.90.0 cargo metadata --locked --offline --no-deps --format-version 1` passed for this repository.
- The attempted baseline `cargo check --locked --offline --no-default-features --features uniffi` stopped at **missing cached `uniffi`**. This is a local dependency-cache limitation, not a compile failure established in the repository. The full native build and 52 tests were not run.
- Isolated scratch `cargo check` probes used **BoltFFI 0.31.1 and Rust 1.90.0**. They confirmed the rejected shapes, the viable alternatives, callback/error signatures, and the 53 adapted ordinary data declarations as described above. They do not build Bark itself.
- No Swift/Kotlin generation, native consumer compilation/execution, AAR/XCFramework build, simulator/device test, CLI build or performance benchmark was performed. These remain migration acceptance work.
- At initial inspection, this assessment was the only repository addition. The follow-up adds the isolated `experiments/boltffi` proof, its consumers, runner and lockfile. Production code, dependencies and build configuration remain unchanged.

## Native proof verification

See [the runnable proof and its limits](../experiments/boltffi/README.md). Rust build/format/Clippy, both native consumer executions, Apple and Android packaging, and generated Swift compilation for iOS Simulator passed. The experiment models the binding surface in memory; it does not depend on Bark, access real wallet data, execute mobile apps, validate daemon shutdown or replace the current SDK. Production migration, the full Bark build/test suite and the companion repository changes remain outstanding.
